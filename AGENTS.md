# RentFlow Agent Instructions

## Project Context

RentFlow is a 2027 Final Year Project and market-oriented digital rental management platform for Tanzanian landlords, tenants and property managers.

Primary message: **One agreement. One payment trail. One source of truth.**

The platform is not a generic property-listing marketplace or US-centric property-management clone. Its core problem is fragmented rental operations after a landlord and tenant enter a rental relationship. Currency defaults to TZS, phone numbers follow Tanzanian formats, payments are mobile-money first through a provider-agnostic layer, and the UI must be mobile-first and low-bandwidth aware. English and Kiswahili should be supported through localization architecture.

## Branching Rules

- `main` is the production/base branch and is conceptually protected.
- Never implement application features directly on `main`.
- The primary development branch is `masterchanges`.
- Always run `git branch --show-current` before editing. If the branch is `main`, stop and switch to `masterchanges`.
- Pull requests must target `main`.
- Agents must never merge their own pull requests.

## Git Authorship Rules

- Preserve the configured repository owner's Git identity.
- Never modify `user.name` or `user.email` unless the repository owner explicitly requests it.
- Never identify an agent, Cursor, Claude, Codex, ChatGPT or similar system as the commit author.
- Never add AI attribution, `Generated by...`, or AI `Co-authored-by` metadata unless explicitly requested by the repository owner.

## Commit Rules

- Use small iterative commits with conventional commit messages (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`, `perf:`, `build:`, `ci:`).
- Commit completed logical units instead of one giant feature commit.
- Inspect `git diff` and `git status` before committing.
- Stage only relevant files.
- Never commit `.env.local`, credentials, access tokens, private keys or real customer data.
- Validate before important commits and before PR creation.

## Product Rules

- Model invoices/rent obligations separately from payments.
- Support partial payments through explicit payment allocations.
- Never mark an invoice paid solely because the browser says a payment succeeded.
- Treat payment callbacks as untrusted external input and process them idempotently.
- Keep payment-provider and notification-provider logic behind adapters.
- Preserve immutable-style financial and tenancy audit history.
- Do not create automated tenant blacklists or represent rental history as a credit score.
- Do not claim electronic agreement acceptance is legally certified unless the implemented mechanism has been independently validated for that claim.
- Do not represent RentFlow as holding security-deposit money unless a compliant custody mechanism has actually been implemented.
- Do not turn the core product into a property-listing marketplace unless the project scope explicitly changes.

## Implementation Rules

- Understand the existing architecture before editing.
- Implement the minimum coherent change that satisfies the requirement.
- Reference `docs/SRS.md` requirement IDs in issues/tests where practical.
- Do not refactor unrelated code.
- Preserve backward compatibility unless intentionally changing behaviour.
- Do not duplicate domain logic.
- Validate all external input.
- Use strong TypeScript types and avoid `any` unless narrowly justified.
- Centralize reusable business logic.
- Prefer server-side execution for trusted operations, authorization and provider integrations.
- Never expose service-role keys, provider secrets or webhook secrets to the client.
- Do not pretend placeholder/sandbox integrations are production-ready.

## Documentation Rules

Documentation MUST change when architecture, schema, environment variables, APIs, setup, workflows, product behaviour, security assumptions or evaluation methods change.

Important documents:

- `docs/SRS.md` — implementation requirements
- `docs/TESTING.md` — quality strategy
- `docs/DEPLOYMENT.md` — environment/release rules
- `docs/FYP_PROPOSAL.md` — academic proposal baseline
- `docs/RESEARCH_AND_EVALUATION.md` — FYP evaluation methodology

## Testing Rules

Every implemented feature should include appropriate validation or automated tests.

Priorities:

- unit tests for rent calculations, allocations, status transitions and validation;
- integration tests for tenancy, authorization, payments, receipts and maintenance;
- end-to-end tests for critical landlord and tenant journeys;
- negative authorization tests across tenants/landlords;
- explicit duplicate-webhook tests for payments.

Follow `docs/TESTING.md`.

## Security Rules

- Secrets only through environment variables or approved secret stores.
- No real credentials or personal research data in commits.
- Enforce server-side authorization and least privilege.
- Protect tenant records and documents from unrelated users.
- Row Level Security is required before any real Supabase production/pilot use.
- Validate uploads and external callbacks.
- Do not log credentials or unnecessary sensitive payloads.

## Database Rules

- Schema modifications go through committed migrations.
- Never casually edit production/pilot data.
- Financial history should avoid destructive rewriting.
- Document schema changes in `docs/DATABASE_SCHEMA.md`.
- Seed/demo data must be synthetic.

## Completion Checklist

Before declaring work finished:

- requirement implemented;
- tests appropriate to the change added/updated;
- lint passes;
- typecheck passes;
- build passes;
- docs updated;
- git status checked;
- commits appropriately split;
- `masterchanges` pushed;
- PR opened against `main` when a delivery unit is complete;
- PR not self-merged by an agent.
