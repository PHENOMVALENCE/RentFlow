# RentFlow Agent Instructions

## Project Context

RentFlow is a 2027 Final Year Project and market-oriented digital rental management platform for Tanzanian landlords, tenants and property managers.

Primary message: **One agreement. One payment trail. One source of truth.**

The platform is not a generic property-listing marketplace. Its core problem is fragmented rental operations after a landlord and tenant enter a rental relationship. Currency defaults to TZS, phone numbers follow Tanzanian formats, payments are mobile-money first through a provider-agnostic layer, and the UI must be mobile-first and low-bandwidth aware.

## Current Repository State

The repository is intentionally documentation-first. The previous application codebase has been removed. Agents must not assume an existing Laravel application exists until it is explicitly initialized and committed.

## Canonical Stack

Unless the repository owner explicitly changes the decision, implement RentFlow as:

- Laravel
- PHP
- Blade + Livewire
- Tailwind CSS
- MySQL 8+
- Eloquent ORM
- Laravel Policies/Gates/middleware for authorization
- Form Requests / Laravel validation
- Laravel Queues/Jobs
- Laravel Scheduler
- Laravel Notifications
- Laravel Filesystem
- PHPUnit or Pest for automated tests

Avoid introducing React, Next.js, Vue, a separate API backend, Supabase-specific architecture, or microservices unless a concrete requirement justifies the added complexity.

## Branching Rules

- `main` is the base/release branch.
- Never implement application features directly on `main`.
- The primary development branch is `masterchanges`.
- Always run `git branch --show-current` before editing.
- Pull requests target `main`.
- Agents must never merge their own pull requests.

## Git Authorship Rules

- Preserve the configured repository owner's Git identity.
- Never modify `user.name` or `user.email` unless explicitly requested.
- Never identify Cursor, Claude, Codex, ChatGPT or another agent as commit author.
- Never add AI `Co-authored-by`, `Generated by...`, or equivalent attribution unless explicitly requested.

## Commit Rules

- Use small iterative commits with conventional prefixes: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`, `perf:`, `build:`, `ci:`.
- Commit completed logical units instead of one giant implementation commit.
- Inspect `git diff` and `git status` before committing.
- Stage only relevant files.
- Never commit `.env`, credentials, access tokens, private keys or real customer/research data.
- Validate before important commits and before PR creation.

## Laravel Implementation Rules

- Follow Laravel conventions before inventing custom framework abstractions.
- Use Eloquent relationships deliberately and avoid N+1 query patterns.
- Put request validation in Form Requests or equivalent reusable validators.
- Use Policies/Gates for resource authorization rather than UI-only permission checks.
- Use database transactions for atomic financial/domain transitions where appropriate.
- Use Services/Actions for reusable business workflows that do not belong in controllers or models.
- Keep controllers thin.
- Use Jobs/Queues for slow external work such as SMS sending, scheduled reminders and retryable provider operations.
- Use Laravel Scheduler for recurring invoice generation, reminder scans and lease-expiry checks.
- Use Laravel Notifications where they provide a clean abstraction over in-app/SMS channels.
- Store secrets only in environment variables/config; access them through Laravel config rather than calling `env()` throughout application code.
- Use migrations for all database schema changes.
- Use factories/seeders with synthetic data for tests and demonstrations.
- Avoid destructive changes to financial/audit data.

## Product Rules

- Model invoices/rent obligations separately from payments.
- Support partial payments through explicit payment allocations.
- Never mark an invoice paid solely because the browser reports success.
- Treat payment callbacks as untrusted external input and process them idempotently.
- Keep payment-provider and SMS-provider logic behind Laravel interfaces/services.
- Preserve immutable-style financial and tenancy audit history.
- Do not create automated tenant blacklists or represent rental history as a credit score.
- Do not claim electronic agreement acceptance is legally certified unless independently validated.
- Do not represent RentFlow as holding security-deposit funds unless a compliant custody mechanism has actually been implemented.
- Do not turn the core product into a property-listing marketplace unless scope explicitly changes.

## Suggested Laravel Domain Boundaries

Prefer clear modules/services around:

- Identity and roles
- Properties and units
- Tenancies
- Agreements
- Billing and invoices
- Payments and reconciliation
- Receipts
- Notifications/SMS
- Maintenance
- Inspections
- Deposits
- Reporting/analytics
- Audit events

Possible implementation locations include `app/Actions`, `app/Services`, `app/Domain`, `app/Jobs`, `app/Notifications`, `app/Policies` and `app/Models`. Do not create directories solely for architectural aesthetics; add them when real code needs them.

## Testing Rules

Every implemented feature should include appropriate tests.

Priorities:

- unit tests for rent calculations, allocations, status transitions and validation;
- feature/integration tests for tenancy, authorization, payments, receipts and maintenance;
- end-to-end/browser tests only where they materially improve confidence;
- negative authorization tests across landlord/tenant/property-manager boundaries;
- explicit duplicate-webhook tests for payments.

Follow `docs/TESTING.md`.

## Security Rules

- Secrets only through `.env` and approved secret stores.
- Never commit `.env`.
- Use CSRF protection for browser forms.
- Enforce server-side authorization using Laravel mechanisms.
- Protect tenant records and private documents from unrelated users.
- Validate uploads, callback payloads and all external input.
- Rate-limit sensitive endpoints where appropriate.
- Hash passwords using Laravel-supported hashing.
- Do not log credentials, OTPs, full secrets or unnecessary sensitive payloads.
- Payment callbacks must verify provider authenticity where supported.

## Database Rules

- Schema modifications go through committed Laravel migrations.
- Use foreign keys and indexes deliberately.
- Never casually edit production/pilot data.
- Financial history should avoid destructive rewriting.
- Document schema changes in `docs/DATABASE_SCHEMA.md`.
- Seed/demo data must be synthetic.

## Documentation Rules

Update docs whenever architecture, schema, environment variables, APIs, setup, workflows, product behaviour, security assumptions or evaluation methods change.

## Completion Checklist

Before declaring implementation work finished:

- requirement implemented;
- authorization considered;
- validation implemented;
- tests appropriate to the change added/updated;
- `php artisan test` passes;
- code formatting/static checks configured for the project pass;
- frontend assets build if applicable;
- migrations reviewed;
- docs updated;
- git status checked;
- commits appropriately split;
- `masterchanges` pushed;
- PR opened against `main` when a delivery unit is complete;
- PR not self-merged by an agent.
